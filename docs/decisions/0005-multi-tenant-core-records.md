# 0005 — Multi-tenant core records (Phase 1)

Status: Accepted
Date: 2026-08-27

## Decision

Auto Bros OS introduces its first business data: shops, staff users, customers, vehicles, and
jobs. Every one of these tables is scoped to a `shop_id`, and tenant isolation is enforced in the
application/service layer, not left to prompting or convention.

## Shops as the tenant boundary

`shops` is the root tenant record. Every customer, vehicle, job, and future domain table carries a
`shop_id` foreign key with `onDelete: "restrict"`, so a shop can never be deleted out from under
records that reference it, and no query can accidentally span shops without explicitly joining on
`shop_id`.

For v1, each staff user (`users` table) belongs to exactly one shop. Dealership and multi-location
support, if needed later, will be a deliberate extension of this model, not a retrofit — the
`shop_id` scoping pattern already generalizes to it.

## Tenant isolation is enforced twice

1. **At the query layer** — every store method takes `shopId` as an explicit parameter and filters
   on it (`WHERE shop_id = $1 AND id = $2`), so a lookup for the wrong shop simply returns nothing.
2. **At the service layer** — after a record is loaded, `requireSameShop(session, record.shopId)`
   (added in `src/auth/authorization.ts`) throws if it doesn't match the caller's own shop. This is
   deliberate defense-in-depth: a bug in one layer's filter doesn't expose another shop's data,
   because the second layer independently checks it. The caller's `shopId` is always taken from the
   authenticated session (`session.user.shopId`), never accepted as caller-supplied input, closing
   off the obvious spoofing vector.

## Job numbering

Job numbers are immutable, human-readable, and shop-scoped: `{PREFIX}-{YEAR}-{SEQUENCE}`, e.g.
`AB-2026-000042`. Each shop configures its own prefix (2–6 uppercase letters) at creation.
Sequence numbers are generated by an atomic `INSERT ... ON CONFLICT (shop_id, year) DO UPDATE
... RETURNING` against a `job_number_counters` table, so concurrent check-ins can never receive
the same number or silently skip one. Once assigned, a job number is never reassigned or reused,
including when a job is put on hold or reopened.

## Job status model

Jobs move through a fixed set of statuses (`checked_in` → ... → `paid_closed`) with an explicit
allowed-transition table in `src/jobs/model.ts`. `on_hold` is reachable from, and returns to, any
other status, matching how shops actually interrupt work (waiting on the customer, a part, a
diagnosis, etc.). `paid_closed` is a true terminal state. Invalid transitions (e.g. jumping straight
from `checked_in` to `paid_closed`) are rejected before they reach the database.

## Universal search is gated by existing permissions, not a new one

Search results are filtered by the caller's existing `customers:read` and `jobs:read` permissions
rather than by introducing a dedicated search permission. A technician (who has `jobs:read` but not
`customers:read` per the existing role matrix) gets job and vehicle results but never customer
results through search — the same boundary they'd hit going through a direct customer lookup. This
was a deliberate choice to avoid creating a side door around the role permission matrix, which
AGENTS.md flags as something that must not be casually modified. The permission matrix itself was
not changed in this phase.

## Duplicate detection

Creating a customer checks for likely duplicates (matching display name, phone digits, or email)
within the same shop before inserting, and raises a distinct, catchable error
(`PossibleDuplicateCustomerError`) rather than silently creating a near-duplicate record or silently
merging. The caller must explicitly confirm (`confirmDuplicate: true`) to proceed. Vehicles use a
stricter rule: a VIN is unique per shop at the database level, so creating a vehicle with an
existing VIN transparently reuses the existing record instead of erroring, since a VIN collision
within one shop is almost always the same physical vehicle.

## Audit coverage

Every create/update path for customers, vehicles, and jobs appends an audit event (`created`,
`updated`, `status_changed`, `assigned`) through the existing `AuditStore`, recording the actor, the
shop, and a before/after snapshot where relevant. This extends the Phase 0 audit framework
(decision covered under Phase 0) to the first real business records instead of introducing a
parallel logging path.

## What is intentionally deferred

- No HTTP routes or UI screens were built in this phase — only schema, migrations, and
  service-layer modules with full test coverage. The check-in screen and other UI land in Phase 2.
- `DatabaseCustomerStore`, `DatabaseVehicleStore`, `DatabaseJobStore`, `DatabaseUserStore`, and
  `DatabaseJobNumberCounterStore` are written for type-correctness and were verified once against a
  real local PostgreSQL database, but are not unit-tested in isolation, matching the existing
  `DatabaseAuditStore`/`DatabaseShopStore` convention from Phase 0.
